The second pass on a failed gate

A failed gate does not start a fix on its own. The orchestrator first sorts the failure by one written rule, so small findings cannot eat the five hours.

Sorted asWhat countsWhat happens
blocksThe build breaks, a test or invariant fails, one of the four use cases is wrong, or a file rule from the brief failsCorrection card, with the gate output attached as it was printed
deferredLint and style warnings, the 400-line limit, and edge cases an operator would rarely meet outside the four use casesOne line in the ledger. Work moves on to review.

Deferred items are picked up in S5 only if time is left. Any still open at the end are listed in the README as known gaps, so nothing is hidden.

The product

What the operator sees when things do not go to plan

The hard part of the brief is a request that may be slow or may be dead, with no way to tell. The design rule: the app never claims to know. It shows how long a request has been outstanding against the engine's normal window and leaves the call to the operator.

earlynormal windowpast window
0 s5 s20 s30 s

Past window is computed from the clock each time the page draws. It is never stored as a state, so it needs no timer and is still correct after a restart.

Workflow 2 of 3

Life of a task

Six stored states. Routing requests and assignments are separate records, so one task can have several attempts and its full story stays readable.

stateDiagram-v2
  state "Needs attention" as NeedsAttention
  [*] --> Unassigned: create
  Unassigned --> Routing: submit
  Routing --> Offered: engine returns a match
  Routing --> NeedsAttention: engine returns no match
  Routing --> Offered: operator assigns by hand
  Routing --> Routing: operator routes again
  Routing --> Unassigned: operator cancels routing
  Offered --> Assigned: contributor accepts
  Offered --> NeedsAttention: declined or offer failed
  Offered --> Offered: operator reassigns
  NeedsAttention --> Routing: operator routes again
  NeedsAttention --> Offered: operator assigns by hand
  NeedsAttention --> Closed: operator closes
  Assigned --> Offered: operator reassigns
  Assigned --> [*]
  Closed --> [*]

The rule that a task has at most one active assignee is enforced by a partial unique index in SQLite, so a code bug cannot break it. Every transition writes its history event in the same transaction as the state change.

Tasks and data

Seed data that fits the reviewer's business

The research desk read the company's public pages. They run an expert marketplace for market research and AI training work: surveys, interviews, ongoing hourly projects, and on the AI side evals, red-teaming and annotation. The seed set uses those kinds of work.

Seed taskNeedsPriorityStarts as

  • Eight fictional contributors, each with one to three areas and room for one or two tasks. Nobody covers veterinary, so a no-match case exists from the first screen.
  • Seed history is produced by replaying real commands against a fake clock, so the seeded timelines are made by the same code as live ones.
  • Every operator override stores a reason code: engine too slow, better fit known, contributor unavailable, priority, other. For an AI company this is the valuable data. Each override is a labelled disagreement with the engine that could later grade a real matcher.
  • Simulation controls sit in their own panel, apart from operator actions: engine outcome per task (auto, fast match, slow match, no match, never returns), contributor reply, a seed, and reset.
Stack and shape

One binary, one command

cargo run starts the server, creates the database and serves the page. There is no Node step, so there is no node_modules to forget when packing. Verified on this machine: Rust 1.99.1 with the MSVC build tools. Crate versions the research desk read from crates.io: axum 0.8.9, tokio 1.54.1, rusqlite 0.42.0.

routing-console/
  src/domain.rs    pure state machine: (state, command) to events or a refusal. No IO.
  src/store.rs     SQLite. One connection behind one lock. One transaction per command.
  src/engine.rs    RoutingEngine trait and the seeded simulator. Owns its own schedule table.
  src/app.rs       load, decide, persist, notify
  src/http.rs      JSON routes, server-sent events, embedded static files
  web/             index.html, app.js, style.css. One render function from one snapshot.
  tests/           transition table, random command runs against invariants, four use cases on paused time
  tools/check/     the file and submission checks below. Standard library only.
  docs/            agent-ledger.md, decisions, research/ with saved pages
  • All writes go through one lock and one transaction. There is no concurrent mutation to reason about, which keeps the explanation short.
  • The simulator decides each outcome from a hash of the seed and the request id, so results do not depend on the order requests happen to run in.
  • Timing tests use tokio's paused clock. Twenty seconds of waiting runs in milliseconds and gives the same answer every time.

How every row gets its test cases

Each of the 11 rows above is tested in batches of five. Haiku agents write the cases, one agent per row, all in parallel. A case is data, not code: the files to create, the outcome the row should give, and one line saying why. A single Opus coder is the only one who writes or changes the checker.

flowchart LR
  rows["11 rules"] --> gen["Haiku, one per rule, in parallel: 5 cases each"]
  gen --> rev{"Is each expected outcome right?"}
  rev -- "no" --> drop["Fix or drop the case, with a note"]
  rev -- "yes" --> run["Run the batch against the checker"]
  drop --> run
  run --> res{"All 5 match for this rule?"}
  res -- "no" --> opus["Single Opus coder edits the checker"]
  opus --> gen
  res -- "yes" --> done["Rule closed, cases kept as regression tests"]
  • I review every case before it runs. A case whose expected outcome misreads the brief is fixed or dropped, so the checker is never bent to fit a wrong test.
  • A rule closes when a fresh batch of five all match. Any miss means the Opus coder edits the checker and that rule gets five new cases.
  • Every case and its result is written to docs/check-cases.md: rule, batch, what was set up, expected, actual, and what was done about it.
  • Limit of three batches per rule. Anything still failing then goes through the second-pass rule: fixed if it blocks, logged if not.

The kind of bug this is meant to catch: a key scan that looks for sk- would flag the word task-routing in every file. Or the 10-file count: does a folder of session files count as one item or as each file inside it? The brief says a folder is sent as one zip, so the cases pin that reading down.

Your calls

Three decisions, all settled

Decision 1 · model ladder · settled

Every coding slice, S0 to S4, runs on an Opus 5.5 subagent at medium effort. Haiku does all fetching. This session plans, reviews diffs and runs the gates.

S2 keeps its own card and its stricter gate, the random command runs against the invariants. If it fails that gate twice, raising the effort on that one card is a one-word change.

Decision 2 · front end · settled

Plain JavaScript served by the Rust binary. One command to run, nothing to install, and the whole front end is one render function you can walk through on camera.

Not chosen: Svelte with Vite. It gives typed components and costs a second toolchain, a build step for reviewers, and about 30 minutes of the box.

Decision 3 · where the build runs · settled

The folder Projects/routing-console now exists as an empty git repository holding the brief, this plan, the research notes and the agent ledger. The build runs in a fresh session rooted there. This session is exported as the planning session.

This session was opened in your home folder, so its export may carry your global instructions and memory index. The redaction check will list what it finds before anything is attached. The folder name leaves the company out on purpose.

Draft for the written answer

Left out on purpose

  • Work after acceptance. The brief says routing is complete once a contributor accepts, so there is no in-progress or done tracking.
  • Automatic retries and timeouts. A pending request is unknown, and the app does not turn unknown into failed. A bounded retry policy is the first thing I would add next.
  • Contributor screens and sign-in. Contributor replies come from the simulation panel. There is one operator and no accounts.
  • A real matching algorithm. The simulator picks the least loaded eligible contributor. The brief says matching quality is not the point.
  • Deployment, multiple servers, and an external queue. One process and one SQLite file.

Stretch, only if S0 to S4 land inside their boxes: an export of overrides as JSON lines, about 15 minutes.
